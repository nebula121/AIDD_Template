# {{PROJECT_NAME}} - コア不可侵ルール

<!-- @spec:core-rules -->

本ドキュメントは、**共通エンジニアリング不変条件（Engineering Invariants）および技術的不可侵境界**を規定する仕様正本（SSOT）である。プロジェクト固有の業務ルール・ビジネス不変条件は [`architecture/domain-rules.md`](architecture/domain-rules.md) を正本とする。いかなる理由があっても本規則に反するコードや仕様を生成してはならない (**MUST NOT**)。

---

## 1. 規範的要件の定義 (RFC 2119)

<!-- @spec:rule-conventions -->

本ドキュメントおよび本プロジェクトの全仕様書におけるキーワードは、RFC 2119 の定義に厳密に従う。

| レベル       | キーワード (RFC 2119)                 | 日本語   | AIDDにおける意味と拘束力                    |
| :---------: | :-------------------------------- | :----- | :--------------------------------- |
| **絶対義務**  | `MUST` / `REQUIRED` / `SHALL`    | 必須・義務 | 例外なく遵守しなければならない。違反するコードや設計は却下される。 |
| **絶対禁止**  | `MUST NOT` / `SHALL NOT`         | 厳禁・禁止 | いかなる理由があっても決して行ってはならない。           |
| **強い推奨**  | `SHOULD` / `RECOMMENDED`         | 推奨    | 正当な理由や事前合意がない限り従わなければならない。        |
| **強い非推奨** | `SHOULD NOT` / `NOT RECOMMENDED` | 非推奨   | 重大な理由がない限り避けるべきであり、採用時はリスクを明記する。  |
| **任意・選択** | `MAY` / `OPTIONAL`               | 任意・許容 | 実装の自由度が認められ、採用可否は開発者・AIの裁量に委ねられる。 |

## 2. アーキテクチャ不可侵境界
<!-- @spec:architecture-boundaries -->

1. **モジュール依存の単方向性 ＆ 循環参照の禁止**:
   * モジュール・コンポーネント間の依存関係は単方向とし、循環参照（循環インポート）を発生させてはならない (**MUST NOT**)。
   * コアロジックは、特定の外部入出力ドライバや具象インフラストラクチャに直接依存せず、関心事を分離しなければならない (**MUST**)。

* **検証基準 (Verification Invariants)**:
  * コードベース全体において、モジュール間の循環インポートが存在しないこと（静的解析・Linterで検証可能であること）。

## 3. セキュリティ ＆ 機密情報保護

<!-- @spec:security-inviolable-rules -->

1. **シークレット完全外部化の原則**:
   - APIキー、アクセストークン、パスワード、秘密鍵などの認証情報は、環境変数または安全なシークレットマネージャ経由でのみ読み出さなければならない (**MUST**)。
   - プレーンテキストの機密情報を、ソースコード、コミットメッセージ、設定ファイル、またはドキュメント内に直接記述（ハードコード）してはならない (**MUST NOT**)。
2. **不可逆・破壊的Git操作の禁止**:
   - バージョン管理において、前進的な追記履歴（Forward-only）を維持しなければならない (**MUST**)。
   - 事前の明示的合意なしに、コミット履歴の改変 (`git push --force`) や、過去ログを破壊・消去するコマンドを実行してはならない (**MUST NOT**)。

- **検証基準 (Verification Invariants)**:
  - コミット対象ファイルにおいて、シークレット検出正規表現 `(?i)(api[_-]?key|secret|password|token)\s*[:=]\s*['"][a-zA-Z0-9_\-]{8,}['"]` による検知が 0 件であること。
  - 自動化スクリプトおよびワークフロー内に `--force` または `-f` オプションを伴う Git 破壊的コマンドが含まれていないこと。

## 4. ライフサイクル別の破壊的変更制御 ＆ テスト隔離原則

<!-- @spec:data-inviolable-rules -->

1. **仕様ステータス（Stability Index）に基づく破壊的変更の制御**:
   - **`status: draft`（試作・初期段階、仕様書未作成ファイル）**:
     - 将来への負債となる不要な下位互換レイヤーや移行アダプタを作成してはならない (**MUST NOT**)。
     - よりシンプルで洗練された設計（Ponytail原則）にするための破壊的変更（スキーマ刷新、API再設計、既存コードの削除）を躊躇なく実施すること (**SHOULD**)。
   - **`status: stable`（確定・保護段階）**:
     - 該当仕様書が対象とするファイル（`target_files`）において、既存の公開インターフェースやデータ構造を損なう破壊的変更を行ってはならない (**MUST NOT**)。
2. **合意なきサイレント破壊の禁止 ＆ 改定プロトコル**:
   - AIが実装の都合やエラー回避のために、仕様書の合意なく勝手に `status: stable` なデータ構造やインターフェースを改変・破壊してはならない (**MUST NOT**)。
   - `stable` なロジックに対して破壊的変更が必要となった場合は、必ず事前に人間に理由と影響を提示して承認を得た上で、仕様書（`docs/specs/*.md`）の改定を先行させなければならない (**MUST**)。
3. **テストデータ完全隔離 ＆ 自動破棄 (Test Data Isolation & Teardown)**:
   - すべての自動テストは、テスト専用の隔離領域（`tmp_path`、インメモリDB、一時ディレクトリ等）で実行され、テスト終了時に確実に自動破棄（Teardown）されなければならない (**MUST**)。
   - テストスイートの実行によって、開発環境の実データ領域、DB、ローカル環境の設定ファイルを汚染・改変・消去してはならない (**MUST NOT**)。

- **検証基準 (Verification Invariants)**:
  - `status: draft` のリファクタリング時、互換ラッパーを残さず旧コード・旧定義が完全に刷新されていること。
  - `status: stable` のコードに対する破壊的変更コミットが、先行する仕様書更新なしに作成されていないこと。
  - テスト実行前後において、実データディレクトリ（例: `data/`）内のファイルハッシュおよびファイル構成に変更が発生しないこと（差分ゼロアサーション）。
